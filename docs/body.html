The one-paragraph version

Observability tells you what failures are happening. This is a record of the step after that: taking one failure cluster from a weak customer-service agent (GLM-5.3-flash under OpenHands, on the τ³ banking benchmark), finding its mechanism, testing four interventions with predictions written first, and then watching the winning one only partly transfer. The loop we ran by hand — trajectory → cluster → hypothesis → intervention → prediction → replicated comparison → held-out test → keep/revise/reject/upgrade-the-model — is the thing worth building tooling for.

1 · Why the score was not enough

HealthBench looked like the harder benchmark and turned out to be the easier one to curate for: its rubric says which weighted points were missed, so one rewrite of the skill moved three tasks from ~0.37 to ~0.69. τ³ scores a task 0 or 1 against an exact expected action sequence. Every failure — a search loop, a wrong product, a skipped step, a message that never reached the customer — scores the same 0. The final score carried no information about which failure had occurred.

The first trajectory we watched live (task 059, “recommend a card and a savings account”) made this concrete: 43 near-identical KB_search calls, zero questions to the customer, and the token budget gone. So the curator built her own measurements from the trajectory: searches per run, customer messages before the first search, repeats of the same top hit, whether verification was ever logged. Those proxy metrics, not the score, are what every later conclusion rests on.

v2 scored 0 on 059 because it recommended Bronze instead of Silver after comparing only the 3–4 products its searches happened to return. v4 (“a claim about the whole category needs the whole list as its source”) passed 059 and, unexpectedly, 050. Fixing one mechanism exposed the next; there was no universal fix.

2 · The biggest cluster: the customer never saw the first message

Across the 22 valid tasks, the most common death was at step 4: start_conversation returns the customer’s opening line, and the model writes “please verify your identity” as a plain assistant reply instead of a send_message_to_user tool call. The harness reads a plain reply as “agent finished”, the customer never receives it, and the episode ends with nothing done. Under baseline this killed 8 of 12 documented runs; under v4, 4 of 12 — even though v4’s skill already stated that the customer only sees text sent through the tool.

Because this is a ~50% coin flip, one run per task cannot detect a change. We measured it as a rate: 4 tasks (018, 044, 050, 101) × 5 replicates per wording, each run killed as soon as the first customer-facing turn resolved.

Two tempting stories that the data killed. (a) The OpenHands harness wraps every skill in a header saying it may be used “for coding style, project conventions, and documentation guidance only”. Removing that header from the prompt changed nothing: 10/20 → 10/20. (b) Saying it louder — “HARD CONSTRAINT, not style guidance. This is not a preference.” with no new information — was the worst arm at 5/20. Twenty-run arms wobble by ±3–4 (v7c at 10/20 shares v6’s content), so the header result should be read with that width too — but neither story survived.

3 · What the hidden reasoning showed

The rendered agent log shows identical steps for deaths and survivals. Dumping the raw upstream response exposed GLM’s reasoning field. On the v7a rerun: runs that emitted no reasoning went straight to the tool (8/8 survived); runs that reasoned survived 7/12, and all five deaths were there. Every death’s reasoning planned the content and never mentioned the channel.

Survived · v9, task 018, replicate 4

Customer
Same opening line.
Hidden reasoning
“Ask for name + verification details before accessing account.”
Emitted
send_message_to_user tool call, finish_reason: tool_calls — “I'd be happy to help you check your cash back rewards. Before I can look at your account details, I'll need to verify your identity…” Customer replies with name, DOB, phone; run continues.

Same customer line, same plan, same sentence — different encoding. The rule in the skill was a fact about the world (“the customer only receives the tool’s argument”), weighed against a plan that was only about words. v9 adds three sentences that restate the rule in the plan’s own vocabulary: “ask the customer”, “tell the customer”, “greet”, “request verification” all name the same single action, a send_message_to_user call. When your plan ends in “let me ask them…”, the next thing you emit is that tool call, not the sentence. Preregistered prediction: ≥17/20, deaths concentrated in reasoning runs. Result: 20/20, with 16 of 20 still reasoning in exactly the old words.

4 · Then the held-out test

Turn-1 survival on 4 tuning tasks is a proxy. The real question is the 22 valid τ³ tasks run end to end. That run finished; it is the most important negative result here.

Reading: the verb binding roughly halved turn-1 deaths on held-out tasks (~50% → 23%) but did not eliminate them — task 050 was 5/5 in the tuning set and died at turn 1 here with the same content-only reasoning (“I need to verify identity first. Ask for name and two identity fields.”). And getting past turn 1 exposed the downstream mechanisms again: 019 and 059, which v4 had passed, went back into search loops and ran out of budget. v9 passed four tasks v4 had not, and lost two v4 had. Net pass rate: unchanged.

Decision on this intervention: retain, but with its scope stated. It is a real, replicated fix for one mechanism on one class of harness (tool-mediated messaging), it does not fully transfer, and it does not move the benchmark by itself because the other mechanisms are untouched. That is exactly the point at which a team should ask whether the next hour goes into the next mechanism or into a larger model.

6 · When is it cheaper to…

Improve the skill
When the model is fixed (cost, latency, on-prem, or the benchmark says so) and the failure has one mechanism you can name. Here: one person-day by hand per mechanism, most of it deciding what to look at next. Worked for turn 1; did not touch search loops or partial-list recommendations.
Use a larger model
When the mechanism is “the model plans content but not channel” or “compares the first few results instead of the list” — a stronger model puts those in the plan for free, and every downstream box in the causal chain disappears. For this cluster it is almost certainly the cheaper fix if the model is not fixed.
Change the harness
When the failure is a channel mismatch the harness could catch (a plain reply to a tool-only customer could be rejected and retried). The header, which looked like the harness lever, was not the cause; the guard would be.
Accept the failure
When the held-out test says the fix moved a proxy but not the outcome and the next mechanism is unrelated — as v9’s 5/20 says here — and the budget is better spent elsewhere.

The business value is not the v9 sentence. It is the loop that reached it and then told us where it stops: fewer expert hours reading traces, shorter feedback iterations, an upgrade to a larger model made only when a targeted fix has demonstrably failed to transfer, and a written reason to abandon an intervention rather than carrying it forward on hope.
